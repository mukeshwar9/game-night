02 / WHAT TO CHANGE

Six focused improvements.

Priorities reflect observed friction and code evidence, not measured conversion loss. P1 is the first pass; P2 is the next product iteration.

P1 · Small–medium Browser + source

Put the game before the game picker.

/solo/tictactoe still renders the full DemoHub selector above the board. Split the explicit solo-play layout from the browsing hub; reuse the existing game components.

src/pages/Demo.jsx:2350–2428
Acceptance checkAt 390 × 844, the entire Tic Tac Toe board and turn instruction are visible without scrolling after choosing solo play. “Change game” remains reachable. Other games need their own board-fit checks.
P1 · Small Keyboard reproduced

Make the options sheet a real focus boundary.

Opening the sheet leaves focus on the catalog card. Pressing Tab moves to its background favorite button, not into the dialog. Add initial focus, a focus trap, background inertness, and focus restoration through the shared sheet.

Use pixel type for character, not every detail.

Mobile card metadata renders at 6–7 px; descriptions disappear below sm. Keep pixel titles and scores, but use 12–14 px mono for metadata and at least 14 px for important instructions. Add visible, programmatic labels for search and room code.

03 / SHIP THE SMALLEST USEFUL PASS

Selected: the focused playability pass.

Your feedback: “lets go with this.” The direction is selected. The scope below is ready for implementation approval; application code is still unchanged.

PASS 1 / SELECTED

Board-first and readable

  1. Use a focused layout for explicit solo routes.
  2. Fix focus management in the shared options sheet.
  3. Raise metadata sizes, keep mobile descriptions, and label inputs.

No game rules, Firebase schema, theme palette, or new routing infrastructure. Keep the existing catalog for /demo.

PASS 2 / AFTER A QUICK USABILITY CHECK

A shorter path to discovery

  1. Make guest entry one action.
  2. Move recent play above the full catalog.
  3. Clarify mode labels; compare copy-only changes with the mode-first concept.

The mode-first concept adds state and changes catalog behavior. Do not ship it solely because the mockup looks cleaner.

Implementation scope and stop condition

  1. Focused solo entry — src/pages/Demo.jsx. On valid /solo/:type routes, show the active game first and put the existing category/grid selector behind a “Change game” control. Keep /demo as the browsing hub. Reuse the existing DEMOS entries, game components, and key-based game reset. Preserve /local/:type behavior and solo play recording. Label explicit solo play as “Solo,” not “Demo.”
  2. Keyboard-safe sheet — src/components/BottomSheet.jsx. Move initial focus into the sheet, contain Tab and Shift+Tab, make background content inert while open, lock background scrolling, and restore the opener on close. Use a portal if needed so background inertness cannot disable the sheet itself. Preserve Escape, backdrop, drag dismissal, and useModalHistory back handling. Restore pre-existing document state on cleanup and handle a removed opener safely.
  3. Readable discovery — src/components/GameCard.jsx, GamePicker.jsx, and src/pages/Home.jsx. Keep pixel game titles; render player count and duration in readable mono type. Show the existing short description on mobile. Add visible labels associated with the search and room-code inputs. Keep search behavior, category/filter persistence, card-to-options flow, and room creation unchanged.

Explicitly out of scope: new home layout, mode-first browsing, onboarding changes, recents reordering, Notes/Emoji Lab navigation changes, lobby layout, game rules, Firebase writes/schema, and theme replacement.

Proof before completion: run unit tests, lint, and production build; compare screenshots at 360 / 390 / 768 / 1440 px; verify the full Tic Tac Toe board at 390 × 844, keyboard focus containment/restoration, 200% zoom, all theme contrasts, and hardware-back behavior where a real device is available. Clearly label any device checks that remain manual.

Stop when: the three selected improvements pass their acceptance checks and existing /demo, /local, search, and room-creation behavior is preserved. Do not expand into Pass 2.

Verification, trade-offs, and what is not covered

Suggested usability tasks: ask a new visitor to play one solo move, create a room for a friend, and find a game for the same device. Ask a returning visitor to resume a room. Observe hesitation, wrong turns, and time to the first move; establish a baseline before claiming improvements.

Regression checks: 360 / 390 / 768 / 1440 px, keyboard-only navigation, 200% zoom, reduced motion, all themes, cold guest entry, returning identity, and back navigation. Test multiplayer in separate browser profiles or devices.

Trade-offs: larger type means fewer visible cards. Deferring customization may reduce early avatar engagement. Mode-first browsing can hide games unless there is a clear “All games” reset. Keep both the full catalog and user identity intact.

Source-only follow-up: the waiting room puts a 150 px QR code before Share/Copy and the room code. Consider mobile share-first and desktop QR-first layouts, but capture a real two-player lobby before prioritizing this change. src/components/WaitingRoom.jsx:254–311.

Not verified: live room creation/joining, reconnects, invites, authenticated Friends/Profile, end-of-round UX, screen-reader output, or gameplay across the whole catalog. This is a focused browser-and-source review, not a full accessibility or performance audit.
