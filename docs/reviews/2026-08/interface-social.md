Already-fixed ground I'm not re-reporting: F-26 (invite/request subscriptions hoisted to app level), F-32 (stats mirrored to `users/{uid}/stats`), F-33 v1 (friends-scoped leaderboard exists), M-19 (friend accept/decline/remove/invite bumped to 44px + confirm-on-remove), M-20 (one-tap PLAY/challenge on friend rows), M-62 (bottom tab bar with Home/Daily/Friends/Profile + badges — this now supersedes the "NavBar has a profile chip" line in UX-IMPROVEMENTS.md, which is stale: the actual `NavBar.jsx` is logo/theme/mute only, nav living in `BottomTabBar.jsx`). ## Detail

**#1 — Identity transparency (Onboarding.jsx, AuthContext.jsx, auth.js).**
`authReady()` (`auth.js:110-129`) fires `signInAnonymously` before the boot splash even resolves — by the time `Onboarding.jsx`'s "PLAY AS GUEST" button renders, the anonymous account already exists. The button is cosmetic; it doesn't consent to anything, it just moves to the next step. Nowhere in onboarding, Home, or Profile is it explained that guest data (friends, stats, avatar) lives only in that browser's Firebase Auth session and disappears if the user clears site data or uses a different browser — the closest is Profile's line "Sign in to keep your profile, avatar, friends & stats across devices," which reads as a benefit pitch, not a risk warning. A player who plays for weeks as a guest, then clears cookies, loses their whole social graph with no prior notice. **Fix:** a one-line disclosure at the guest choice ("Guest — saved on this device only, no account needed") mirrors what Chess.com/similar do, and costs one string.
Structural certainty (verified by reading `authReady()`/`Onboarding.jsx` directly) — no rendered check needed.

**#2 — Silent data loss on upgrade collision (auth.js:150-172).**
The file's own comment says it plainly: "That Google account is ALREADY a Firebase user... we fall back to signing into it — the current guest's data is then orphaned (merging is out of scope for v1)." This is a real, documented data-loss path — a guest who has built up friends/stats, then signs in with a Google account they'd previously used on another device, loses everything they built as a guest with no warning dialog, no "this Google account already has data, continue anyway?" step. The success toast ("SIGNED IN — YOUR PROFILE IS NOW SAVED ACROSS DEVICES!") outright misrepresents what happened in this branch — the *previous* profile carries over, not the guest session that was just abandoned. **Fix:** detect the collision before committing (a cheap `codes`/`users` lookup) and confirm with the player, or at minimum change the success copy for this branch.
Structural certainty from source + comment; the actual popup/redirect UX would need a live check to confirm exact wording shown.

**#3 — Leaderboard interface (leaderboard.js, Friends.jsx:363-433).**
`fetchFriendsLeaderboard` pulls `wins`/`losses`/`games` straight from `users/{uid}/stats`, which is a lifetime sum across every game type (already flagged as a data problem by another review; this is the interface consequence). A friend who plays 40 rounds of Pong ranks above a friend who plays TicTacToe once a week purely on volume — the leaderboard rewards being logged-in and grinding a fast game, not being good at anything specific. There's also no time window (a win from three months ago weighs the same as one from this morning, so a currently-inactive friend can sit at #1 indefinitely) and no per-game cut, despite `getGameConfig`/`GAME_TYPES` already providing everything needed to slice by game type. As an interface it currently answers "who has played and won the most, ever, at anything" — not a question a player asking "am I good at this game" or "who's hot this week" actually has. **Fix, sequenced:** (a) default to a rolling window (7-day is the obvious retention hook, matches the Daily Challenge cadence already in the product) with an all-time toggle; (b) let the existing game-select dropdown that already drives "PLAY" also filter the leaderboard, so one control does double duty instead of the board silently mixing game types. Both are pure client-side reshaping of data already fetched — no new Firebase rules needed.
Structural certainty from source; can't be confirmed against a rendered UI I haven't seen.

**#4 — Avatar identity expression (avatars.js:11-34, AvatarCustomizer.jsx:104-112).**
`SHAPES` holds 20 fun creature glyphs (invader, robot, ghost, wizard, ninja, dino, slime, etc. — all still fully rendered by `Avatar.jsx` and valid via `isValidAvatar`), but `PICKER_SHAPES = HUMANOIDS` restricts the actual customizer UI to exactly 2 base bodies, and the UI prints the raw shape name ("BOY"/"GIRL") as the only label under the preview. So "customizing an avatar" is really "pick one of 2 bodies, then recolor 4 clothing slots from 6 theme tones" — the interesting art (20 shapes' worth) is dead code from a player's perspective, and identity expression is thinner than the screen real estate (a full page section in onboarding, another full section in Profile) implies. This also means every avatar is visibly gendered by design with no non-binary/neutral shape option and no way to opt back into the creature set that's already built and tested. **Fix:** the code comment at `avatars.js:29-31` already flags this as reversible — "Re-enabling creatures in the picker later = point PICKER_SHAPES back at SHAPES" — so re-adding at least a few creature shapes to the picker (even alongside boy/girl) is a one-line change with an already-built renderer, tone system, and default-avatar hashing behind it.
Structural certainty from source; the "worth the screen it takes" judgment is subjective and my own.

**#5/#6/#7/#8 — Small craft gaps.** Profile's SAVE button (`Profile.jsx:153-160`) is `py-2` with no `min-h-11`, unlike every other action button on the same page (COPY/SHARE at `min-h-11`) — an inconsistency, not a one-off oversight, since the pattern is already established two elements away. AvatarCustomizer's RANDOM button (`AvatarCustomizer.jsx:150-156`) is `px-2 py-1.5` around 9px text, under WCAG 2.2's 24px floor, while the tone swatches right next to it correctly wrap in `min-w-11 min-h-11`. Tone swatches (`AvatarCustomizer.jsx:131-149`) differentiate purely by fill color with only an `aria-label` as the non-visual fallback — fine for screen readers, thin for low-vision/colorblind sighted use. The three `focus:outline-none focus:border-retro-p1` inputs (Profile name, Friends code entry, Friends challenge-game select) replace the browser's default focus ring with a 1px border color change, a materially weaker signal for keyboard users tabbing through the form. All four are structural certainties from Tailwind classes; the last would benefit from an actual contrast/visibility check under each of the 6 themes since `retro-p1` differs per theme.

## What's missing

- **A "why should I care about a friend" hook beyond PLAY.** Trace it end to end: a friend row shows online/offline, PLAY (creates + invites a room), and remove. That's the entire relationship surface. There is no way to see what a friend has been playing, no shared game history between the two of you specifically (Profile's HEAD TO HEAD block exists but is keyed by opponent *name*, is local-only, and isn't surfaced from the Friends page at all — you'd need to already know to check Profile), no "X just beat Y at Connect Four" activity feed, nothing that makes a friend feel like an ongoing thread rather than a standing invite target. Right now "friend" functionally means "a shortcut to start a room with," which is real utility but thin for the amount of infrastructure built (codes, requests, presence, bidirectional writes).
- **Per-friend match history / rivalry record.** The uid-keyed stats mirror (`users/{uid}/stats`) already exists per F-32; a `matches/{uid}/{matchId}` append-log keyed by both uids is the natural next node and would retroactively power a real head-to-head view, a leaderboard time window, and an activity feed, without new architecture — just a write at the same point `recordMatch` already fires.
- **Any signal of *why* the leaderboard changed.** Even with a time window, a bare rank number tells a player nothing about the match that moved it. A one-line "beat Sam at Connect Four, 2 hours ago" under a rank change would close the loop the boot screen's fake high-score marquee (noted in UX-IMPROVEMENTS.md) already promises but the real leaderboard doesn't pay off.
- **Friend-code entry has no scan/share-link fast path on Friends itself.** Profile and Friends both have COPY/SHARE for *your own* code, and WaitingRoom has a QR flow for room invites, but adding a friend is manual 6-character typing only — no camera/QR add, despite the QR infrastructure already existing one page away for a different purpose.

## Well built, one line each

- **Friend-code entry (`normalizeFriendCode`/`isValidFriendCode`, Friends.jsx:234-241):** live-filters invalid characters as you type, uppercases automatically, and a typo resolves to a clear "NO PLAYER WITH THAT CODE" rather than a generic error — a good mobile hand-entry flow.
- **Friends list & leaderboard rows (Friends.jsx):** 44px targets, confirm-before-destructive-remove, and the leaderboard rows being made directly tappable (challenge/view-self) rather than decorative — genuinely resolves M-19/M-20/M-89 as claimed.
- **Avatar.jsx:** clean theme-token-only rendering, proper `role="img"`/`aria-label`, zero hardcoded hex — a model citizen for the color-rules constraint.
- **BottomTabBar.jsx:** correctly wires `requestCount`/`inviteCount` badges from `AuthContext`, 44px targets throughout, safe-area-aware — resolves M-62 for real (unlike the stale NavBar claim in UX-IMPROVEMENTS.md).

## Structural vs. needs-rendered-check

Everything above is a structural read from source (Tailwind class math, control flow, comments admitting behavior). Nothing in this review required a browser. Two items would benefit from a live/rendered check if anyone wants to go further: #8 (actual focus-ring visibility per theme — six `--c-*` palettes could make the border-color swap adequate in some themes and not others) and #6/#7's real rendered pixel size (Tailwind arbitrary text sizes plus font-pixel line-height aren't 100% predictable from the class alone).

Dataset-cited: #5, #6 (Touch Target Size / Target Size (Minimum)), #7 (Color Only), #8 (Focus States) — all via the UI/UX Pro Max search tool, `ux` domain.
